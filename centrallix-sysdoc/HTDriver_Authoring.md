## I. Introduction
A DHTML Widget Driver (or just a widget driver) generates DHTML code (in HTML, CSS, and JavaScript) to represent a widget in a browser.  This document explains how to author a widget driver, including how to use the DHTML generation interfaces.  Thankfully, this is much simpler than authoring an [object system driver](OSDriver_Authoring.md).

Centrallix has two types of widgets: visual and nonvisual.  Visual widgets usually represent some UI element like a button, edit box, or table.  Nonvisual widgets usually represent functionality, such as form widgets, event-action connector widgets, and parameter widgets.


## II. Centrallix DHTML Page Model
When Centrallix generates a DHTML page, it outputs several sections containing data from DHTML drivers.


### HTML Header
The HTML page header consists of code between the `<head>` and `</head>` tags in the page.  This includes (in order):
- Style sheet declarations.
- Page header items, such as META tags, the page title, etc.
- A `<style>` section where HTML drivers can write CSS rules.
- A `<script>` block to declare global variables for HTML drivers.
- A section for HTML drivers to include any scripts they will use.
- A `<script>` block with several generated functions to handle setting up the events system, defining and building the widget tree, and running all the driver initializations for the page.


### Event Handlers
Widget drivers may install event handlers which generate registration code in the [HTML page header](#html-header).  Centrallix implements its own event handling system, which is similar to DHTML event handling.  However, these events operate entirely at the top-level "document", with no "trickle-down" or "trickle-up" event processing model.

Event handlers are functions that are called *any time* a particular event occurs anywhere on the page.  Thus, they usually need to detect if the event occurs to HTML managed by the driver (e.g. when a button handles a click event, it needs to detect if it was clicked, or if something else on the page is being clicked).  This is usually done by "tagging" the generated HTML with an attribute (e.g. "kind") to identify the widget.


### Initialization
Almost all drivers need to run some JS to initialize each widget they create.  This code is typically written in a startup function in an included `.js` file, and called from the page header when the page finishes loading.


### HTML Body
The HTML `<body>` tag contains the HTML content generated by HTML drivers.  It can also hold some special parameters set by HTML drivers, although many of these are deprecated or obsoleted by CSS.


## III. Page Generation Process
To generate a page, the HTML generation subsystem renders the page by [`Render()`](#function-render)ing its top-level widget (usually a page widget).  When an HTML driver is rendered, it should:

1.  Use OSML or wgtr calls to get any info it needs about the widget instance (e.g. its location, background, etc.).  Use other drivers as a reference for which functions to call and read their doc comments to learn how to call them.
2.  Call DHTML APIs to add any HTML, CSS rules, JS init calls, event handlers, global variables, etc. to the data structures for the [sections of the page](#ii-centrallix-dhtml-page-model).
3.  If the widget is allowed to contain subwidgets, render any that are specified.  These *may* be placed in a container opened in step 2, but that is not required.
4.  Write HTML to close any open containers, and clean up (if necessary).

Thus, once the top-level widget is rendered, every widget on the page (all children of it) should also have been rendered by its driver.  Then, the HTML generation subsystem writes the data from its data structures into the HTML page.


## IV. HTML Generator Interface
The HTML generator interface includes 1 optional function (`Setup()`) and 1 required function (`Render()`) for HTML drivers to implement, as described below.  Implementing a driver also requires it to be initialized (using an [HtDriver struct](#htdriver-struct)) when Centrallix starts up.

### Initialization
Every HTML driver must initialize a driver struct in an `xxxInitialize()`, where 'xxx' is the module's [abbreviation prefix](OSDriver_Authoring.md#abbreviation-prefix).

The initialization process should include:
1. Allocating a new [HtDriver struct](#htdriver-struct) using `htrAllocDriver()` and setting the appropriate fields.
2. Initializing any module internals / globals.
3. Registering the driver struct in the HTML generation subsystem using `htrRegisterDriver()`.
4. Indicating driver support (e.g. for DHTML) by calling `htrAddSupport()`.

These initialize functions should be called by `cxHtInit()` in [centrallix.c](../centrallix/centrallix.c).  They should return 0 on success or a negative error code if an error occurs.


### HtDriver Struct

| Attribute    | Type             | Description
| ------------ | ---------------- | -----------
| Name         | `char[64]`       | A descriptive name for the driver.
| WidgetName   | `char[64]`       | A one-word name for the widget, used as the widget's type when declaring it in a structure file. Thus, a widget declared using "widget/widgetname" should specify "widgetname" for this property.
| Setup        | Function Pointer | An optional function, called the first time a driver is used in a new session / on a new page.
| Render       | Function Pointer | A required function, called to render a driver's content.

All other elements of this structure are "private" and should not be accessed or modified directly by the widget driver.  Instead, use the appropriate API functions to specify these values.

- 📖 **Note**:  If you look at the already-implemented drivers in the Centrallix distribution, many of them *do* access these directly.  This is legacy code that was not cleaned up when these functions were added to replace it.


### Function: Setup()
```c
int htxxSetup(pHtSession s);
```
The driver may optionally implement `Setup()`, which is called the first time a driver is used in a new session.  In other words, it's called once before the first instance of a widget renders on a new page or dynamic component.  This is useful for generating DHTML data shared by all instances of a widget, such as shared CSS rules.

This function is passed 1 parameter:

| Parameter | Type          | Description
| --------- | ------------- | ------------
| s         | `pHtSession`  | The generation session, passed as context to call most `htr*()` functions.

This function should return 0 when successful, or return -1 and call `mssError()` if an error occurs.


### Function: Render()
```c
int htxxRender(pHtSession s, pWgtrNode tree, int z);
```
The driver must implement `Render()`, which generates an instance of a widget into the page.

This function is passed 3 parameters:

| Parameter | Type          | Description
| --------- | ------------- | ------------
| s         | `pHtSession`  | The generation session, passed as context to call most `htr*()` functions.
| tree      | `pWgtrNode`   | The widget tree node to render, which has the widget properties.
| z         | `int`         | The widget's CSS z-index.  Pass `z + 1` (or higher) when rendering children so they stack above it.

This function should return 0 when it successfully generates a widget, or return -1 and call `mssError()` if an error occurs while rendering.


## V. Page Generation Functions
The HTML generation subsystem provides several functions that HTML drivers should use to add data to the [sections of the page](#ii-centrallix-dhtml-page-model).  Many functions have an `_va` variant that uses a qprintf format and accepts arguments to fill it.

The following list is a quick reference/index for the most commonly used functions, not an exhaustive list.  For information about calling these or a complete list of functions, read the doc comments in [ht_render.c](../centrallix/htmlgen/ht_render.c) or use other HTML drivers as examples.

### Getting Data
- `wgtrGetPropertyType()`
- `wgtrGetPropertyValue()`
- `htrGetBoolean()`:  Reads a widget property as a boolean value.
- `htrGetBackground()`:  Generates background CSS from a widget's properties.
- `wgtrRenameProperty()`:  For deprecated properties that can't be removed yet.

### Writing CSS
- `htrFormatElement()`:  Adds a CSS rule to position and style an element, supporting *many* common widget properties.
- `htrAddStylesheetItem()` / `htrAddStylesheetItem_va()`:  Adds CSS to the `<head>` style block.

### Writing HTML
- `htrAddHeaderItem()` / `htrAddHeaderItem_va()`:  Adds HTML to `<head>`.
- `htrAddBodyItem()` / `htrAddBodyItem_va()`:  Adds HTML to `<body>`.

### Writing JS
- `htrAddScriptInit()` / `htrAddScriptInit_va()`:  Adds JS that runs after the page loads.
- `htrAddScriptCleanup()` / `htrAddScriptCleanup_va()`:  Adds JS that runs on page unload.
- `htrAddEventHandlerFunction()`:  Registers a Centrallix event handler.
- `htrCheckAddExpression()`:  For client-supported widget properties.
- `htrAddScriptGlobal()`

### Linking Widgets
- `htrAddWgtrObjLinkage()` / `htrAddWgtrObjLinkage_va()`:  Sets the DOM element that represents a widget on the client.
- `htrAddWgtrCtrLinkage()` / `htrAddWgtrCtrLinkage_va()`:  Sets the client-side object containing a widget's children.

### Rendering Children
- `htrRenderSubwidgets()`:  Render all child widgets.  For most drivers, this is all you'll need.
- `htrRenderWidget()`:  Render a specific widget.  Useful for drivers that render certain subwidgets but use the registered driver for others.
- `htrCheckNSTransition()`
- `htrCheckNSTransitionReturn()`

### Registering Drivers
- `htrAllocDriver()`
- `htrRegisterDriver()`
- `htrAddSupport()`


## VI. Designing your Widget
The first step is normally to decide on a basic design for the widget.  Consider issues below when building a design:

- What and how many HTML elements should be used?  These should be kept to a minimum to avoid unnecessary complexity and computation in browsers.  Nonvisual widgets can often work with almost no HTML because they mainly introduce logic with JavaScript.
- How will the widget look?  How should a user interact with it?
- How will a user *try* to interact with your widget "incorrectly", and how should it respond?
- Will the widget receive mouse, keyboard, and/or data focus?  If keyboard focus, it should receive keyboard input.
- Whether the widget receives keyboard focus or not, will it use hotkeys?
- What events (mouseup, mousedown, etc.) does the widget need to handle?
- Can the widget contain visual subwidgets?  If so, where will they appear in the widget?
- Can it contain nonvisual subwidgets?  Most widgets allow this so app designers can use child connectors to handle events near the code where they occur.
- Will the size of the widget's contents change over time?  If so and if the widget can contain visual subwidgets, then it may need to set some values to interact with the `pg_resize()` mechanism.  How will the widget behave when resized, both by `apos.c` on the server and client-side by its own CSS and resize handlers?

Sometimes it can be helpful to draft the widget's design by simply creating a DHTML page outside Centrallix that does some of what you need.
